# Миграции и подключения backend

Локальный API (`APP_ENV=local`) перед стартом применяет миграции отдельным пулом до двух соединений (Flyway использует отдельное соединение для PostgreSQL lock), затем открывает рабочий пул и проверяет схему. Если заданы оба `MIGRATION_DATABASE_USER` и `MIGRATION_DATABASE_PASSWORD`, миграционный пул использует их. Для старой локальной `.env` допустим fallback на `DATABASE_USER`/`DATABASE_PASSWORD`. Рабочий пул не использует миграционные credentials. При отсутствии `APP_ENV` backend выбирает production и не применяет миграции при запуске API.

В production API **не выполняет DDL**. Перед запуском процесса с `APP_ENV=production` отдельно выполняют `./gradlew runMigrations` (Windows: `./gradlew.bat runMigrations`) с `DATABASE_URL`, `MIGRATION_DATABASE_USER` и `MIGRATION_DATABASE_PASSWORD`. Этот запуск не требует JWT secret, использует свой пул и увеличенный socket timeout для DDL. После успешного завершения API стартует с `DATABASE_USER`/`DATABASE_PASSWORD` прикладной роли и проверяет историю Flyway; при невыполненной или неверной миграции не принимает трафик. Прикладной роли нужны SELECT к `flyway_schema_history` и права DML к рабочим таблицам, но не DDL. Существующий локальный `.env` не переносить на production.

`DATABASE_MAX_POOL_SIZE`, `DATABASE_CONNECTION_TIMEOUT_MS`, `DATABASE_STATEMENT_TIMEOUT_MS` и `DATABASE_LOCK_TIMEOUT_MS` ограничивают рабочий пул и транзакции. Значение lock timeout должно быть меньше statement timeout. При планировании нескольких процессов и worker суммарное число соединений держат в пределах бюджета PostgreSQL. `poolSnapshot()` даёт active/idle/waiting/total для будущих метрик; чтение snapshot не заменяет измерение p95. Миграционный пул не наследует короткий runtime socket timeout.

Рабочий пул допускает от 2 до 100 соединений: проверка схемы Flyway при запуске использует два соединения. Значение `DATABASE_MAX_POOL_SIZE=1` отклоняется при чтении конфигурации, до ожидания соединения при запуске.

`withJdbcTransaction` выполняет write-транзакцию на IO dispatcher. `withReadOnlyJdbcTransaction` даёт короткий согласованный снимок для нескольких запросов. `withRetryingJdbcTransaction` повторяет всю транзакцию только при deadlock/serialization SQLSTATE; вызывающий код обязан держать внешние эффекты вне повторяемого блока. Advisory key `pointCreation` и ключи адресатов централизованы в `AdvisoryLockKeys`; все использующие их сервисы должны соблюдать один порядок захвата.

При отмене coroutine эти два JDBC helper отправляют PostgreSQL cancel request и закрывают физическое соединение через JDBC `abort`. Одного закрытия сокета недостаточно для немедленной остановки серверного запроса. `cancelSignalTimeout=2` ограничивает каждое ожидание подключения/чтения cancel request; `statement_timeout` остаётся защитой при недоступной сети. Наблюдатель отмены использует отдельную elastic IO view с параллелизмом не больше размера пула, чтобы заблокированные SQL-запросы и ожидающие подключения не занимали все доступные ему IO-потоки. Helper дожидается завершения наблюдателя до возврата соединения пулу, проверяет отмену перед commit и сохраняет исходную ошибку вместе с ошибками cleanup в suppressed exceptions.

Ожидание самого подключения по-прежнему ограничено `DATABASE_CONNECTION_TIMEOUT_MS`: уже отменённый вызов после получения соединения не начинает SQL. Отмена одновременно с уже начавшимся commit может оставить неизвестный клиенту исход; для повторов используются существующие идемпотентные операции. Отдельный readiness probe через Exposed сохраняет свой `statement_timeout=5s` и не использует этот механизм отмены.

`configureTransport` включает штатный Ktor `HttpRequestLifecycle` с `cancelCallOnClose=true`: обнаруженное Netty закрытие клиентского соединения отменяет контекст соответствующего запроса и запускает отмену его JDBC-работы. Интеграционный тест с реальным HTTP/1.1 TCP RST во время SQL проверяет остановку запроса PostgreSQL, rollback и сохранение другого keep-alive соединения. Потеря сети без обнаруженного закрытия остаётся ограниченной сетевыми и SQL timeout. Текущий plaintext connector не включает h2c; проверка HTTP/1.1 не является свидетельством поведения HTTP/2.

Для локального нагрузочного измерения `DATABASE_POOL_JMX_ENABLED=true` регистрирует Hikari MBeans; по умолчанию значение `false`, а включение при `APP_ENV=production` запрещено. Этот флаг не запускает management agent и не открывает сетевой порт. Локальный sampler в `tools/load/` подключается через JDK Attach к PID принадлежащего прогону процесса и читает только active/idle/total/waiting у `roy-db`. Нагрузочный runner использует local-only management agent без remote JMX port; адрес коннектора и системные свойства не записываются в свидетельства.
