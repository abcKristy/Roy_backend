# T150. Локальные сценарии гонок B6

Входной backend — `0a2ac71`, API v1, Flyway V001–V016. Входы — [фикстуры](fixtures.md), [REST-сценарии](api-cases.md) и [требования](requirements.md). Состояния ниже задают допустимый результат. Для фактического результата нужен отдельный протокол.

## Общий барьер и oracle

1. Для каждого повтора создать новый экземпляр fixture либо новый namespace в одноразовой PostGIS. Зафиксировать actors, исходные revision, count, seq, активную бронь, настройки и jobs. Для каждого запроса открыть отдельную сессию клиента. Взять реальные UUID и значения из fixture или ответов REST.
2. Подготовить оба запроса целиком. Поставить два рабочих потока перед I/O на `ready(2)` / `start(1)`. Дождаться обоих `ready` и одновременно открыть `start`. Гонка подтверждается пересечением временных интервалов или ожидающими транзакциями. Две последовательные команды не считаются этим сценарием.
3. Для управляемых порядков использовать существующую тестовую остановку после начала транзакции или отдельное соединение с `SELECT … FOR UPDATE` на строке, которую в штатной операции блокируют оба запроса. Проверить ожидание через `pg_blocking_pids(pid)` и `pg_locks` в третьем соединении. Затем освободить gate или зафиксировать первый запрос и отпустить второй. Для разных ресурсов соблюдать порядок T4, уже используемый операциями. Для сетевых jobs ставить gate после claim или расшифровки, до вызова локального fake sender. Внутри production-транзакции не ждать ответа провайдера.
4. Дождаться завершения обеих транзакций и клиентов. Снять HTTP/status и стабильный `error.code`, затем read-back в новом соединении и через REST. Для WS записать тип события, id/seq и отсутствие незакоммиченного или повторного события. Фиксировать старт/финиш монотонными часами, безопасные requestId, владельца и результат блокировки, SQLSTATE без параметров, SHA, Flyway, среду, ожидаемое и фактическое состояние. Порядок HTTP-ответов не используется как источник `bookingOrder`.
5. Предельное ожидание gate — 10 с, завершения пары — 30 с. Превышение фиксировать как ошибку прогона с диагностикой, а не как допустимый бизнес-отказ. Gate освобождать в `finally`, незавершённые соединения закрывать, затем очищать только fixture. Не включать в протокол JWT, токены, телефоны и текст сообщений.
6. Для каждой применимой пары провести 3 независимых повтора каждого управляемого порядка и 10 повторов одновременного старта. Указывать фактическое число повторов. Один существующий JUnit-сценарий доказывает только реально выполненный набор порядков, остальные результаты остаются `NOT_RUN`.

## RACE-001 — последний слот квоты

- Требования — `B6-MAP-02`, `B6-MAP-03`, `API-041`, `API-044`.
- Барьер и запросы — A имеет ровно один доступный слот (2/3 за 7 суток или 9/10 за 30 суток). Два `POST /api/v1/points` от A с разными UUID ключей, двумя допустимыми координатами дальше 100 м от существующих точек и друг от друга. На управляемых прогонах менять порядок захвата строки аккаунта A.
- Oracle — ровно один 201 и один 409 `POINT_QUOTA_EXCEEDED`. Только одна новая точка, один граф и одна запись создания. Второй запрос сохраняет предусмотренную блокировку на 30 суток и терминальный результат ключа. Точный повтор второго ключа не продлевает блокировку. Дальнейший новый ключ при активной блокировке даёт 409 `POINT_QUOTA_BLOCKED`.
- Ориентиры — `PointWriteServiceIntegrationTest`, `PointQuotaBlockRouteIntegrationTest`, `M2MonthlyQuotaBoundaryIntegrationTest`.

## RACE-002 — одинаковый ключ создания

- Требования — `B6-MAP-02`, `API-041`.
- Барьер и запросы — A с запасом квоты посылает два `POST /api/v1/points` одновременно, один ключ UUID. На первой копии тела равны. На второй копии выбрать два допустимых разных адреса или позиции и развернуть порядок захвата аккаунта.
- Oracle — для равных тел оба получают 201 с одним pointId. Для разных тел один 201 и один 409 `IDEMPOTENCY_KEY_REUSED`. В обоих вариантах только один граф, одно создание и один успешный snapshot ключа. Содержимое соответствует победившему запросу. Проверить, что повтор после потерянного ответа не создаёт ещё один граф.
- Ориентиры — `PointWriteServiceIntegrationTest`, `M2LostTcpCreateResponseIntegrationTest`, `M2AtomicCreateFailureIntegrationTest`.

## RACE-003 — дубль темы и autojoin

- Требования — `B6-MAP-02`, `B6-CHAT-01`, `API-046`.
- Барьер и запросы — A/B с отдельными токенами добавляют к существующей P одну и ту же custom-тему с разными ключами и нормализуемыми вариантами регистра/пробелов. Оба запроса конкурируют за P. Использовать два тела из `TopicUnicodeUniquenessIntegrationTest`.
- Oracle — один 201, один 409 `DUPLICATE_TOPIC`. Один topic с каноническим ключом, один chat, autojoin победившего actor и ровно одно соответствующее системное событие. Отказ не оставляет членство проигравшего или пустой чат.
- Ориентиры — `TopicUnicodeUniquenessIntegrationTest`, `AddTopicAutojoinIntegrationTest`, `M2QuotaTopicFilterAcceptanceIntegrationTest`.

## RACE-004 — дубль жалобы и порог mute

- Требования — `B6-CHAT-03`, `API-038`, `API-004`.
- Барьер и запросы — A одновременно посылает две жалобы на B из общего K с разными ключами. На второй fixture к 15 lifetime-жалобам одновременно добавить жалобы от двух разных допустимых участников. Барьер — конкурентная запись по одному target, обе сессии проверены.
- Oracle — для одной пары один 201 и один 409 `DUPLICATE_REPORT`, одна запись и увеличение lifetime на один. Для разных reporters обе операции 201, итог 17 уникальных записей. Переход mute только на 16-й, срок ровно 7 суток от первого перехода, повтор и 17-я в активном mute его не продлевают. Чтение B работает, отправка в mute даёт 403 `MESSAGE_MUTED`.
- Ориентиры — `ReportTransactionIntegrationTest`, `ReportLifetimeIntegrationTest`, `MuteThresholdIntegrationTest`.

## RACE-005 — вступление и уход последнего участника

- Требования — `B6-CHAT-01`, `B6-MAP-02`, `API-047`, `API-048`.
- Барьер и запросы — A единственный активный участник K и P. A отправляет DELETE membership, B отправляет PUT membership. Оба запроса без ключей и тела. Удерживать gate строки P.
- Oracle — если вступление первым, PUT 200 и DELETE 204, P остаётся с B, A покинул K. Если уход первым, DELETE 204 и PUT 404 `RESOURCE_GONE`, P и пустой граф удалены. Нет активной связи с удалённым графом или живой P без участников. Повтор PUT при существующей P не удваивает связь.
- Ориентир — `PointJoinLastLeaveRaceIntegrationTest`.

## RACE-006 — отправка и уход того же участника

- Требования — `B6-CHAT-01`, `B6-CHAT-02`, `API-004`, `API-048`.
- Барьер и запросы — A отправляет валидный TEXT с новым ключом и одновременно покидает K из другой access-сессии A. B остаётся участником и подписан на WS K. Использовать gates send-first / leave-first из существующего теста.
- Oracle — send-first даёт 201 и 204, B видит ровно одно TEXT с неизменным seq и один факт ухода. Leave-first даёт 204 и 403 `NOT_MEMBER`, TEXT и его WS-событие отсутствуют. В обоих случаях A больше не читает K, B сохраняет историю.
- Ориентир — `ChatSendLeaveRaceIntegrationTest`.

## RACE-007 — голосование и бронирование

- Требования — `B6-MEET-01`, `B6-MEET-02`, `API-011`, `API-012`.
- Барьер и запросы — до startsAt у Q два активных голоса A/B и revision R. A бронирует с R и новым ключом, B одновременно снимает голос. Проверить оба порядка под gate P. Отдельно запустить два PUT `going=true` от одного actor при исходном отсутствии его голоса и два PUT от разных actors.
- Oracle — unvote-first даёт 200 и 409 `STALE_STATE` для старой R. Book-first даёт 201 и 200, последняя транзакция отменяет бронь при goingCount=1 и инвалидирует будущие reminders. Итог обоих порядков — ни одной активной брони с ≤1 голосом. Два одинаковых голоса одного actor дают одну строку и один переход revision. Два разных голоса дают две строки и только один переход в ready.
- Ориентиры — `MeetingConcurrencyIntegrationTest`, `BookingVoteConcurrencyIntegrationTest`, `BookingCancellationPolicyIntegrationTest`.

## RACE-008 — бронирование и закрытие автором

- Требования — `B6-MEET-02`, `API-012`, `API-013`.
- Барьер и запросы — открытый Q, A автор и проголосовал, B проголосовал. Из отдельных сессий A одновременно book и close с одинаковой свежей R и разными UUID ключей. Менять первый доступ к gate P.
- Oracle — при close-first close 200, book со старой R получает 409 `STALE_STATE`, новой брони нет. При book-first book 201, close со старой R получает 409 `STALE_STATE`, одна бронь остаётся активна. Повторное закрытие с актуальной revision и новым ключом отменяет её и jobs в транзакции. Не допускается закрытый Q с активной бронью. После startsAt проверить отдельный 409 `MEETING_ALREADY_STARTED`.
- Ориентиры — `MeetingConcurrencyIntegrationTest` для барьера встреч, `BookingAuthorCloseIntegrationTest`, `BookingCancellationEventsIntegrationTest`.

## RACE-009 — одновременные пересекающиеся брони

- Требования — `B6-MEET-02`, `API-012`.
- Барьер и запросы — два предложения на одной P с частичным пересечением интервалов, готовые голоса и независимые ревизии. Синхронные book с разными ключами и `confirmOverlap=false`. После обоих ответов повторить отклонённый сценарий с актуальной revision, новым ключом и `confirmOverlap=true`.
- Oracle — первая транзакция 201, вторая 409 `OVERLAP_CONFIRM_REQUIRED`. После подтверждения второй booking получает следующий серверный bookingOrder, обе записи допустимы, приоритет у меньшего bookingOrder. Ни время отправки, ни порядок HTTP-ответов не влияют на него. Отдельная копия с соседними непересекающимися интервалами допускает оба 201 без подтверждения.
- Ориентиры — `BookingOverlapConfirmIntegrationTest`, `BookingPairwisePriorityIntegrationTest`.

## RACE-010 — отключение extra и создание предложения

- Требования — `B6-NOTIFY-01`, `B6-NOTIFY-02`, `API-008`, `API-032`, `API-035`.
- Барьер и запросы — C с обоими extra, актуальным согласием, опорной позицией ≤1 км и активной установкой. A создаёт Q в чате без C, C выключает оба extra с актуальной R. Две независимые сессии и gate перед записью уведомления адресату или перед захватом настроек.
- Oracle — если настройки изменены первыми, событие и jobs для C отсутствуют. Если proposal первым, видимое событие остаётся в истории, ожидающая доставка отменена, последующее создание не выбирает C. В обоих порядках центр C удалён, дальний D не выбран, другие каналы и адресаты не меняются.
- Ориентиры — `JdbcNotificationWriterIntegrationTest`, `ProposalEventsIntegrationTest`, `NotificationRoutesIntegrationTest`.

## RACE-011 — повторный claim, отмена и перепривязка

- Требования — `B6-NOTIFY-02`, `B6-MEET-02`, `API-012`, `API-029`.
- Барьер и запросы — для активной своевременной брони в UTC-окне задержать два scheduler ticks после обнаружения одного booking. На другой копии остановить воркер после claim или decode и до I/O, параллельно отменить бронь либо перепривязать установку. Повторить с gate уже внутри локального fake sender для проверки позднего ack.
- Oracle — один логический reminder на адресата и не больше одной job на installation/event, повтор после restart сохраняет notificationId. Если отмена/перепривязка завершилась до отправки, fake sender получает ноль вызовов по старому получателю. Поздний ack уже начатого вызова не отменяет новый статус и не отзывает свежую привязку. Факт ранее принятого провайдером сообщения отозвать нельзя.
- Ориентиры — `ReminderSchedulerIntegrationTest`, `BookingReminderCancellationIntegrationTest`, `DeviceRebindDeliveryConcurrencyIntegrationTest`, `JobsIntegrationTest`.

## RACE-012 — идемпотентное чтение и гонка замены аватара

- Требования — `B6-NOTIFY-01`, `B6-PROFILE-01`, `API-024`, `API-026`, `API-034`.
- Барьер и запросы — две сессии A одновременно ставят read одному видимому N. На отдельной fixture два PUT multipart на аватар из общего исходного состояния A. Для медиа использовать локальный AvatarStore с gate после staging обоих объектов и до CAS ссылки.
- Oracle — оба read возвращают 200 с одним readAt, C получает 404 `RESOURCE_GONE`. При двух заменах, начавшихся с одной ссылки, допустим один 200 и один 409 `STALE_STATE`. В БД один актуальный указатель, прежний объект имеет cleanup, временный проигравший объект удалён или поставлен на долговременную очистку. Защищённое чтение выдаёт только актуальный файл.
- Ориентиры — `NotificationHistoryIntegrationTest`, `AvatarSwapRoutesIntegrationTest`, `AvatarReadRoutesIntegrationTest`.
