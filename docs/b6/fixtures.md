Дата фиксации — 07.11.2026. Исполнитель — агент проверки T148. Входы — [паспорт кандидата](baseline.md) и [реестр требований](requirements.md). Backend `0a2ac71`, миграции V001–V016. Общий `seedVersion` — Git-дерево `src/test` `2dfc98735bd19e1f24ad05c6123be9aa1cd36a19`. Источник конкретного seed указан в строке. Каталог описывает программу B6, новые результаты случаев имеют статус **NOT_RUN**. Исторические факты приведены в [T145](../m5-b54-b55-local-handoff.md) и [протоколах M2](../m2-server-fixture-passport.md), [M3](../m3-server-fixture-passport.md), [M4](../m4-meeting-acceptance.md).

## Роли, геоданные и время

- **G** — гость без токена и строки членства. **A** — владелец, создатель точки/предложения или активный участник, **B** — отдельный активный участник и второй проголосовавший. **C** — авторизованный неучастник целевого чата. В nearby C может быть получателем с актуальным согласием и добровольным центром. **D** — дополнительный синтетический субъект для другого чата, дальнего центра, устаревшего согласия либо другой установки. Уточнение роли всегда указано в случае.
- Для отрицательного запроса C проверяется отдельная действующая сессия. В начальном состоянии убедиться, что C не состоит в целевом чате и в других чатах проверяемой точки. В сценарии смены состава до запроса проверяется `chat_memberships.left_at` и доступ к истории. Удалённый пользователь и участник, вышедший из чата, ведутся как отдельные состояния.
- Все номера, пароли, содержимое, device IDs и ключи — синтетические, создаются внутри сценария. Значения токенов и SQL bind parameters не помещать в отчёт. Для идемпотентного повтора использовать один выданный сценарным клиентом ключ. Для отдельной операции нужен новый UUID.
- Координаты — WGS84/SRID 4326 в порядке longitude, latitude при записи через PostGIS. Радиусы сравниваются в метрах. Для случаев 100 м/1 км seed строит пограничную геометрию в PostGIS, а проверка использует точное расстояние. Для совместного MVP вручную задано `(37.62, 55.75)`.
- Для обычных запросов `t0` — фактический UTC-инстант сервера или БД на входе сценария. Относительные смещения должны быть теми же при повторе. Внедрённые `Clock` используются только там, где это предусмотрено исходным тестом. В тесте с управляемыми часами запись берётся из часов фикстуры, а не из часов машины. Случайные UUID меняются при повторе, логический граф, состояния и смещения остаются одинаковыми.

## Безопасный сброс и запуск

1. Использовать [правила изоляции](../integration-test-safety.md). Создать принадлежащий запуску временный локальный контейнер из уже доступного образа PostGIS с динамическим пробросом только на `127.0.0.1`. Проверить уникальные имя/ID и label контейнера, host/port и требуемый алиас. Не импортировать рабочую БД, пользовательские номера или реальные токены.
2. На отдельной БД применить и сверить V001–V016. Для FX-AUTH-UPGRADE использовать пустую `template0` и дать тесту выполнить миграции. Для FX-POINT-VIEWPORT/FX-POINT-M2 выполнить SQL с `ON_ERROR_STOP` и соблюсти проверяемое имя. Для FX-POINT-FILTER клонировать подготовленный viewport graph. После seed проверить принадлежность строк и нулевое активное членство C в целевом графе.
3. Установить `TEST_DATABASE_DISPOSABLE=true` только после подтверждения владельца. Передать локальные тестовые credentials, `TEST_DATABASE_URL` или `TEST_VIEWPORT_DATABASE_URL` без credentials/query и выполнить `gradlew.bat --offline integrationTest --tests com.example.<класс>` либо соответствующий набор из `tools/b6/suites.json` через `tools/b6/run.ps1`. Сохранить case ID, backend SHA, схему, fixture ID/seedVersion и безопасный JUnit результат. Пропущенный тест имеет статус NOT_RUN.
4. Каждый повтор начинать с новой одноразовой базы/контейнера или чистого клона требуемого seed. Не делить алиас между классами, которые проверяют полные counts, используют одинаковые фиксированные номера или оставляют доменные строки. Разные aliases в таблице означают разные физические базы. Один и тот же обязательный алиас может потребовать разные контейнеры и динамические порты.
5. Остановить сервер и WS-клиенты. Применять только очистку по собственным UUID/ключам, встроенную в fixture. После сверки владельца остановить конкретный временный контейнер. `--rm` удаляет этот экземпляр. Временную приватную папку медиа очищать в границе собственного test root. Для неуспешного прогона сохранить безопасный JUnit/лог до очистки. Общую, пользовательскую и production БД не сбрасывать.
