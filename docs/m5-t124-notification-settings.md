# M5 T124. Обновление настроек уведомлений

Изменения проверены в ветке `feat/notification-settings` на базе `0b0c13986e91c062ed3afbc6500f33fcf49d1cca`. Одноразовая фикстура использовала PostgreSQL 18.6, PostGIS 3.6.4 и все 15 миграций до V015 включительно.

## HTTP-контракт

`PUT /api/v1/me/notification-settings` принимает четыре JSON Boolean и неотрицательное целое Int64 `expectedRevision`. При совпадении ревизии ответ `200` содержит сохранённые флаги и увеличенную `revision`. При конфликте `409 STALE_STATE` содержит в `error.details` те же пять полей из строки текущего аккаунта, прочитанной под блокировкой перед сравнением ревизий. Эти пять полей составляют весь объект `details`. После конфликта клиент может перечитать настройки через `GET`.

## Исполненные сценарии

- Два одновременных PUT с `expectedRevision: 0` и разными флагами дали один `200` и один `409 STALE_STATE`. Тело `200`, `error.details` ответа `409` и последующий GET совпали с набором флагов победителя и ревизией 1.
- После двух успешных записей повтор исходного запроса дважды дал `409 STALE_STATE` с последними флагами и ревизией 2. Последующий GET вернул те же флаги и ревизию.
- SQL-бэкфилл из ресурса V006 создал недостающую строку со значениями `true / true / false / false` и ревизией 0. После пользовательской записи два повторных запуска того же SQL затронули по 0 строк. GET оба раза вернул изменённые флаги и ревизию 1.
- Запросы со строкой вместо Boolean и со строкой вместо `expectedRevision` дали `422 INVALID_FIELD`. Незавершённый JSON дал `400 INVALID_JSON`. После каждого запроса GET вернул исходные флаги и ревизию 0.
- GET и PUT без `Authorization` дали `401 AUTH_REQUIRED`. Авторизованный GET подтвердил исходные флаги и ревизию 0. В фикстуре используются подписанный JWT и тестовый `SessionRepository`.
