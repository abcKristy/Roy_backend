# M1.T6.B03 — negative auth cases

This is the server-side case set for `S-M1-AUTH` in the [M1 passport](m1-server-acceptance-passport.md). Run against an isolated database with a published policy valid for that environment. Use generated synthetic accounts and record only case ID, backend commit, schema version, HTTP status/code, `requestId`, and aggregate DB assertions. Do not retain passwords, access/refresh tokens, phone numbers or SQL parameters in the evidence. Expected results below are source-derived; none is a captured run from this document.

1. **A01 duplicate phone.** Register the same synthetic phone twice with the current policy. First request: `201 Session`; second: `409 DUPLICATE_PHONE`. Compare user/session/notification-settings row counts before and after the second request: no additional rows may remain after rejection.
2. **A02 underage and invalid fields.** Register with `ageYears=11`, then with malformed E.164/short password. Each is `422 INVALID_FIELD`; no user, session or settings row is created. A missing required JSON property is also `422 INVALID_FIELD` at transport validation.
3. **A03 stale or absent publication.** Supply an outdated or empty `acceptedPrivacyPolicyVersion`: `422 PRIVACY_POLICY_ACCEPTANCE_REQUIRED` with safe `details.currentVersion`, no writes. Without an available published policy the route returns `503 SERVICE_UNAVAILABLE` before hashing or writes. An omitted required version is the separate transport `422 INVALID_FIELD` case.
4. **A04 bad login.** Unknown phone and wrong password both return the same `401 INVALID_CREDENTIALS` message, without a new `auth_sessions` row. This is a form rejection; the client must not classify it as expired session or call refresh.
5. **A05 expired or revoked access.** `GET /api/v1/me` with an expired, forged or revoked access JWT returns `401 SESSION_EXPIRED`; a missing Authorization header returns `401 AUTH_REQUIRED`. No protected mutation occurs. An access 401 alone does not prove that the refresh token is invalid.
6. **A06 refresh rotation and replay.** A valid refresh returns `200 Session` with a new token pair and unchanged session deadline. Reuse the old refresh token: `401 SESSION_EXPIRED`; the replay revokes that session, so its current access and refresh credentials fail. Check the session row's revocation state, not token text in logs. A malformed token also yields `401 SESSION_EXPIRED` but is not evidence of replay revocation.
7. **A07 one-session logout.** Create two sessions for one account; `POST /api/v1/auth/logout` with session A returns `204` and revokes only A. Reusing A yields `401 SESSION_EXPIRED`, while session B still passes `/me`. Check the two `auth_sessions` rows. Logout A also prevents its refresh.
8. **A08 network failure.** Disconnect before a refresh response. There is no reliable HTTP status or error body, so the client must keep its token snapshot and show a retryable network state. A later retry can receive `401 SESSION_EXPIRED` if the server already rotated the token; only that definitive response clears the pair. Do not queue or replay online mutations automatically.

`RegistrationRouteTest`, `LoginRouteTest`, `RefreshRouteTest`, `SessionRouteTest` and their JDBC integration counterparts provide focused source-level scenarios. For this M1 server acceptance, record actual HTTP and database side effects separately on a disposable environment. A passing unit test or a listening port is not a server acceptance result. Mark unexecuted cases **NOT RUN** in the protocol; Android/iOS behavior belongs to the later mobile pass.
