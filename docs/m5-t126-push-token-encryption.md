# T126. Шифрование токенов push-установок

Backend читает `PUSH_TOKEN_ENCRYPTION_KEY_BASE64` из окружения процесса. Значение должно кодировать 32 случайных байта в Base64. В `.env.example` поле пустое. Некорректное непустое значение останавливает запуск с сообщением, содержащим только имя параметра и причину отказа. При пустом или отсутствующем значении сервер запускается, а аутентифицированный запрос регистрации с корректным ID установки получает `503 PUSH_REGISTRATION_FAILED`.

Запись `device_registrations` содержит `token_ciphertext` и `token_digest`. Формат ciphertext — `v1:` и Base64 от 12-байтового случайного nonce, шифротекста AES‑256‑GCM и 16-байтового тега. Установка и серверное обозначение платформы входят в AAD. Детерминированный SHA‑256 digest применяется для уникальности активного токена в пределах платформы. Повтор того же запроса возвращает прежний `registeredAt`. Worker передаёт расшифрованный токен в `PushSender` при доставке.

## Результаты проверки

Backend `24696d7` с правками T126. PostgreSQL 18.6 и PostGIS 3.6.4, одноразовая БД `roy_m5t126_crypto`, Flyway V001–V016. В тестах создавались временные синтетические ключи и токены. Для прогона с ключом фикстура передавала значение в штатный загрузчик `ServerConfig.fromEnvironment`, после чего запускала Ktor-модуль и использовала реальную PostgreSQL.

- Без ключа исходный модуль вернул `404` вместо ожидаемого `503`. После правки аутентифицированный PUT вернул `503 PUSH_REGISTRATION_FAILED`, строка установки отсутствовала. PUT без JWT вернул `401`.
- Некорректный Base64 остановил запуск. Декодированный ключ длиной 31 байт также отклонён. Диагностика исключений не содержала проверочных значений.
- С ключом PUT вернул `200`. Проверка полной строки установки не нашла открытый токен. Сохранённый digest совпал с отдельно вычисленным SHA‑256. Идентичный повтор вернул тот же DTO и сохранил строку без изменений. Другая учётная запись с тем же токеном получила `409 DEVICE_TOKEN_IN_USE`.
- Неверный ключ при разборе задания дал `FAILED / INVALID_TOKEN`, отправщик не вызывался, привязка осталась прежней. При повторе задания с верным ключом контролируемый отправщик получил исходный токен, задание перешло в `SENT`. Это проверка границы расшифровки и передачи аргумента.
- Unit-тесты подтвердили разные nonce при повторном шифровании, расшифровку при исходном AAD и отказ при подмене ID установки, платформы или байта шифротекста.

`PushTokenEncryptionIntegrationTest` — 4 успешных сценария. `DeviceTokenCipherTest` — 4 успешных теста. `DocumentationRoutesTest` — 5 успешных тестов. OpenAPI 3.1 проверен по 45 маршрутам и 431 примеру.

## Эксплуатационный блокер

Ключ и хранилище секретов для среды развёртывания остаются недоступны. Синтетические ключи использовались только во время проверки. Реальная доставка через RuStore/APNs и ротация ключа с сохранением существующих привязок ожидают эксплуатационной проверки. Связанный блокер — `provide-push-token-encryption-key`.
