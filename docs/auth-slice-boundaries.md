# M1.T2: границы auth-среза

Сервер — отдельный Gradle- и Git-проект. Мобильный клиент будет независимым проектом после создания каркаса M1.T3. Контракт между ними — REST/JSON v1 из M0.T5; общий модуль DTO и прямая Gradle-зависимость не создаются.

## Серверная часть

Этот репозиторий отвечает за `GET /api/v1/legal/privacy`, `POST /api/v1/auth/register`, `POST /api/v1/auth/login`, `GET /api/v1/me` и `POST /api/v1/auth/logout`. Сервер валидирует данные и актуальную версию политики, хранит хеш пароля и подтверждение согласия, выпускает JWT и проверяет запись `auth_sessions` при каждом защищённом запросе. Регистрация создаёт пользователя, сессию и настройки уведомлений в одной транзакции.

Публикация утверждённого текста политики с постоянным URL и метаданными предшествует приёму согласия. Если утверждённого текста нет, регистрация остаётся недоступной.

## Передача мобильному проекту M1.T3

Клиентский auth-срез размещается в будущем независимом `project/mobile` после создания shell в M1.T3. Его common-контракты включают `AuthRepository`, `SessionRepository` и порт `SecureSessionStore`; платформенные реализации хранят токен через Android secure storage и iOS Keychain. Два экрана регистрации и входа используют MVI и передают shell одноразовые действия `AuthSucceeded` и `SessionExpired`. Shell выполняет навигацию и закрывает доступ к персональному состоянию при подтверждённом `401` защищённого запроса. Сетевой сбой не удаляет сессию; публичные запросы не несут старый Bearer.

Серверные маршруты сами по себе не закрывают M1.T2. Готовность задачи требует интеграции обоих экранов и защищённого хранилища на Android и iOS после появления shell M1.T3.
