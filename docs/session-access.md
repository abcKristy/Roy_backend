# M1.T2 protected session access

`GET /api/v1/me` and `POST /api/v1/auth/logout` require `Authorization: Bearer <access JWT>`. Missing authorization returns `401 AUTH_REQUIRED`. Invalid, expired, forged or revoked sessions return the same `401 SESSION_EXPIRED` response. Login's public `401 INVALID_CREDENTIALS` remains a separate form error.

The verifier checks the HS256 signature, `sub`, `jti`, `authVersion`, `iat` and `exp`. Every protected call then queries `auth_sessions` joined with the active `users` row, requiring a non-revoked, unexpired session and matching `auth_version`. The repository runs JDBC work off the event loop. Logout updates only the current `jti`; another session belonging to the same account remains active. A repeated logout with the revoked token receives `401`.

`GET /me` returns the full v1 `UserSelf` shape. These routes do not depend on the draft privacy policy. Unit/route checks cover token rejection, profile response and local revocation. The JDBC integration test runs only when `TEST_DATABASE_URL` points to a disposable `roy_m1t2_*` database; it checks one-session revocation, database expiry, auth version and deleted users. It skips when that variable is absent.

## Token renewal

Registration and login return `accessToken`, `expiresAt`, `refreshToken`, `refreshExpiresAt` and `user`. The access JWT is short lived (default 15 minutes, `JWT_TTL_SECONDS`). The opaque refresh token belongs to the same database session, whose lifetime is fixed at creation (default 30 days, `REFRESH_TTL_SECONDS`). The server stores only a SHA-256 hash of the refresh token. Both tokens are secrets and must be kept out of logs.

Send `POST /api/v1/auth/refresh` with JSON `{"refreshToken":"..."}` before or after access expiry. A successful call atomically replaces the refresh token and returns a new token pair. Replace both client-side values together; never keep using the old refresh token. The client must serialize refresh attempts (single flight): concurrent calls using the same token can be treated as replay and revoke the session. Renewal does not extend `refreshExpiresAt`. A rejected refresh returns `401 SESSION_EXPIRED`; only then should the client clear both tokens and require login. A network failure must leave both tokens intact; a retry may still return `401` if the first rotation succeeded but its response was lost. When the session expires, is revoked, or its user's auth version changes, the client must log in again. Logout revokes the database session, so its refresh token also stops working. Existing sessions created before the refresh migration retain their access JWT until expiry but cannot refresh.
