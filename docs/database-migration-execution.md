# Выполнение плана изменения БД

Источник: `../../../plans/database/database-migration-plan.md` относительно этого файла; план находится вне данного Git-репозитория. В журнале фиксируются только выполненные шаги и проверенные факты без паролей, токенов и содержимого пользовательских строк.

## Шаг 0 — инвентаризация и резервная копия, 01.11.2026

Состояние: выполнено для локальной БД. Ветка `data/database-migration` создана от актуальной `origin/main` (`bd8d2d42e40881aff5e6be54f3f0e840278550d7`); перед созданием рабочая копия была чистой.

- Среда: `APP_ENV=local`, draft privacy включена; БД `roy` в локальном Docker Compose, PostgreSQL 18.6, PostGIS 3.6.4. Docker показывает 20 CPU и 8 185 561 088 байт памяти. Это характеристики среды разработки, не целевого сервера.
- История Flyway в БД: V001 (`1186265143`), V002 (`-1231202910`), V003 (`-1571061539`), все успешны. V004 есть в Git, но не применена к этой БД. В БД 11 пресетов тем, 25 индексов и 2 пользовательских триггера; набор таблиц соответствует V003.
- Точные количества: `users`, `auth_sessions`, `points`, `point_topics`, `chats`, `chat_memberships`, `notification_settings`, `point_creation_events`, `operation_idempotency` — по 0 строк. Следовательно, дефектов существующих пользовательских связей и backfill-строк сейчас нет; условия миграции всё равно рассчитаны на заполненную БД других сред.
- Резервная копия создана **до изменений схемы**: `.local/backups/roy-before-v005-20261101-223621.backup`, формат pg_dump custom, размер 34 681 байт, SHA-256 `B0E2AAC014D230D4107CC821D69461ED55A13E8057A8EDA369CAFB9A6CB8C455`. Каталог `.local/` исключён из Git.
- Архив восстановлен в **отдельную** БД `roy_migration_restore_20261101`. У исходной и восстановленной БД совпали точные количества девяти пользовательских таблиц и checksums всех трёх миграций. Исходная `roy` при проверке не менялась.

Автор проекта подтвердил пределы MVP: `q` 3–256 Unicode-символов, тело сообщения ≤4096, причина жалобы ≤1000, адрес ≤512; завершённые служебные jobs хранить 30 суток после терминального состояния. Лимит HTTP JSON body ≤16 КиБ — техническая настройка backend, при необходимости изменяемая без изменения продуктового контракта. Автор также указал ориентир на первые 1–2 года: **до 100 пользователей, около 350 точек, примерно 20 сообщений на пользователя (около 2 000 сообщений)**. Для будущего прогона подготовить профиль этого масштаба и отдельно плотный синтетический стресс-набор для оценки роста (например, 100 000 точек, 1 000 000 пользователей, 10 000 000 сообщений и 10 000 000 событий). Стресс-набор не является прогнозом аудитории. Оборудование production пока неизвестно и должно быть зафиксировано до нагрузочной приёмки.

Проверка шага: восстановление pg_restore завершилось без ошибки; SQL-сравнение counts/checksums совпало; статус Git перед записью журнала проверен. Никакие тесты приложения и миграции в этом шаге не запускались. Следующее действие по плану — подготовка backend (шаг 1), затем применение V004 перед V005.

## Шаг 1 — инфраструктура backend, 01.11.2026

Состояние: выполнено. Добавлены отдельный миграционный пул и команда `runMigrations`, production API только проверяет историю Flyway и отказывает в старте при отставании, ошибке или более новой схеме. Локальный API применяет миграции до открытия рабочего пула. Отсутствующий `APP_ENV` трактуется как production. Настройки размера пула, ожидания соединения, statement/lock timeout валидируются. Добавлены обычная и read-only REPEATABLE READ транзакции, ограниченный retry `40P01`/`40001`, транзакционные advisory keys. Изменяющие auth-запросы users используют `FOR NO KEY UPDATE`. Новые продуктовые маршруты и worker пока отсутствуют, поэтому доступа к незавершённой схеме они не открывают. Инструкция развёртывания находится в `docs/database-runtime.md`.

Проверка: целевые тесты `DatabaseBootstrapIntegrationTest` и `ServerConfigTest` прошли на отдельной `roy_m1t2_step1bootstrap`; четыре класса auth JDBC integration прошли каждый на собственной отдельной БД. На восстановленной копии `roy_migration_restore_20261101` команда `runMigrations` успешно применила существующую V004. Пробный production API на исходной `roy` (V003) отказал в старте до приёма трафика из-за отсутствующей V004; исходная БД осталась на V003. Первые полные прогоны тестов выявили недостаточный размер миграционного пула и коллизии фиксированных данных между интеграционными классами при общей БД; пул исправлен до двух соединений, классы проверены в изолированных БД. Повторное read-only ревью после исправлений: APPROVE без существенных замечаний. Отдельные учётные записи migrator/runtime локально пока не созданы; production требует выдать им права согласно `docs/database-runtime.md` до развёртывания.

## Шаг 2 — схема V005–V012, 01.11.2026

Состояние: выполнено для локальной и изолированных тестовых БД. Добавлены счётчик активных участников с транзакционным backfill/trigger, индексы и проверки существующих таблиц, сообщения и rate events, pg_trgm GIN для подстрочного поиска, жалобы, предложения/голоса/брони, устройства/позиции/события уведомлений и устойчивые jobs. Всего 21 прикладная таблица; кроме них в public есть служебные `flyway_schema_history` и PostGIS `spatial_ref_sys`. Внутренний nullable `notification_events.booking_id` фиксирует конкретную бронь для reminder/booking-событий без публичного target и без FK, чтобы сохранить историю после удаления брони.

Проверка: Flyway применил V001–V012 к отдельной пустой `roy_migration_clean_final_20261101` и V004–V012 к копии исходной V003 `roy_migration_upgrade_final_20261101`; повторный запуск на каждой БД сообщил «No migration necessary», все 12 checksums валидны. Ранее восстановленная из резервной копии `roy_migration_restore_20261101` успешно прошла V004–V012 при репетиции; она содержит старый тестовый checksum V007 до исправления NULL-ветки и больше не является финальной контрольной БД. V005–V008 отдельно проверены на копии V004 с заполненным чатом: INSERT/leave/rejoin/DELETE membership и каскадное удаление чата согласуют счётчик. На финальной пустой БД SQL-проверки отвергли SYSTEM без `system_type`, PROCESSING без claim/lease и reminder без внутреннего `booking_id`. Четыре класса auth JDBC integration (registration/login/refresh/session) прошли каждый на собственной копии V012. Read-only ревью V005–V012: APPROVE после исправления CHECK для NULL system_type и конфликта имени CHECK в V011.

Локальная `roy` тоже теперь V012; в девяти исходных пользовательских таблицах по-прежнему 0 строк, все 12 записей Flyway успешны и checksums валидны. Причина более раннего применения к `roy`, чем планировалось: ошибка PowerShell в проверочной замене URL оставила исходный адрес; команда была выполнена до финального изолированного прогона. Это обнаружено по журналу Flyway и сразу сообщено автору. После исправления команды финальные прогоны выполнены на явно проверенных отдельных URL. Резервная копия шага 0 сохранена и проверена восстановлением; данные `roy` не удалялись. Последующее исправление CHECK V007 уже было в версии, применённой к `roy`, поэтому V013 и ручное изменение Flyway history не потребовались.

Граница шага: продуктовые маршруты, worker и отдельные роли migrator/runtime ещё не реализованы/не созданы; это следующие этапы плана. Backend шага 1 проверяет точную версию миграций и не запустит бинарную версию с меньшим набором миграций на V012, хотя схема сохраняет физическую совместимость auth-запросов. Нагрузочная приёмка остаётся отдельным шагом.

## Шаг 3 — транзакционные операции и уведомления, 01.11.2026

Состояние: инфраструктура выполнена. `JdbcIdempotencyOperations` блокирует actor `FOR NO KEY UPDATE`, сравнивает канонический SHA-256 hash операции/route IDs/бизнес-полей, возвращает replay/conflict и сохраняет terminal SUCCESS или QUOTA_EXCEEDED в транзакции вызывающего кода. Флаги подтверждения и expectedRevision исключены из hash. Квотный отказ сам повторно берёт actor-lock, получает `clock_timestamp()` после блокировки, вычисляет +30×24ч и строит обязательный response snapshot из фактического срока. Новые success-записи тоже требуют snapshot. `JdbcSystemMessageWriter` под chat row-lock выделяет `message_seq`, сверяет принадлежность чата точке и пишет SYSTEM payload T5 в ту же транзакцию; время берётся из БД после lock.

`JdbcNotificationRecipients` выбирает действующих адресатов чата и nearby <=1000 м внутри READ COMMITTED business transaction. `RecipientBarrier` берёт весь набор shared/exclusive advisory locks в общем порядке и проверяет активность адресата новым statement после lock. `JdbcNotificationWriter` сохраняет deduplicated event и jobs действующих установок, снимает канал/видимость/push из текущих настроек, не пишет событие удалённому адресу или extra без opt-in, проверяет обязательные внутренние target IDs по event_type. Все операции принимают переданный Connection, внешнюю доставку не вызывают. Публичные маршруты и worker отсутствуют; подключение этих операций в `Server.kt` потребуется вместе с соответствующими use cases на следующих шагах, чтобы не создавать неиспользуемые объекты.

Проверка: `JdbcCoreOperationsIntegrationTest` на отдельной `roy_m1t2_step3core4` V012 прошёл (hash/replay/conflict, квотная запись и DB-время, выделение seq/rollback). `JdbcNotificationWriterIntegrationTest` на отдельной `roy_m1t2_step3notify` V012 прошёл (channel/settings/dedupe/device jobs/barrier, обязательные target ID, chat/nearby выборка и исключения). Финальное read-only ревью: APPROVE после исправления времени квоты, обязательного snapshot и typed targets. До публичного центра уведомлений нужен безопасный типизированный builder `displaySnapshot` с title/body без PII; конкурентные сценарии deletion/fanout и rebind/delivery остаются проверками шагов 7–9.

## Шаг 4 — точки, темы и членства, 01.11.2026

Состояние: выполнено для backend. Добавлены публичные GET пресетов, bbox-карты и карточки точки; защищённые GET контекста создания/квоты; POST точки и темы; PUT/DELETE членства. Карта фильтрует bbox/тему/число участников до LIMIT, использует подписанный keyset cursor и пакетно выбирает все темы и число уникальных участников точек страницы. Публичные маршруты не зависят от наличия auth-сервиса, защищённые требуют действующую сессию. Квота считается по скользящим 7×24/30×24 ч; создание берёт глобальный advisory lock, actor и point/chat locks, повторно проверяет 100 м и квоту, затем атомарно пишет point/topic/chat/membership/ledger/SYSTEM/idempotency. Тема и join записывают SYSTEM и курсор. Leave снимает голоса, отменяет активную бронь при снижении до ≤1, инвалидирует reminder jobs, пишет системные/notification события и удаляет точку после ухода последнего участника. Собственный голос бронирующего нужен при создании брони; после его ухода бронь с ≥2 оставшимися голосами сохраняется согласно M0-T5. Внешний геокодер не вызывается внутри DB-транзакции; ручной адрес допускается контрактом.

Проверка: `PointReadRepositoryIntegrationTest` прошёл на `roy_m1t2_step4read`; `PointWriteServiceIntegrationTest` на `roy_m1t2_step4write` (create/replay/nearby/add/join/leave, SYSTEM seq, отмена брони и notification job, удаление пустой точки, квота 4/7 и 11/30 с сохранённым отказом); `PointWriteSnapshotIntegrationTest` на `roy_m1t2_step4snapshot`. `PointRoutesIntegrationTest` на чистой `roy_m1t2_step4routesfinal` прошёл через HTTP create/replay/map/detail/last leave; route-тесты проверили INVALID_BBOX/INVALID_FIELD, неизвестный preset, отсутствие Idempotency-Key и публичный map route без auth-сервиса. Все БД отдельные V012. Read-only ревью: APPROVE после исправлений Unicode-длины, near preview position, membership DTO и ошибок фильтров. Конкурентный double-create/join-vs-leave и нагрузка остаются приёмкой шага 9; WebSocket и внешняя доставка ещё не включены.
